Production System · Context

The 3-3-3 Method
— Context

The reference spec for what the agent operates on, what it produces, and what "good" looks like. Input requirements, the ten-category improvement taxonomy, the improvement-log format, implementation patterns, and the six core principles.

Section 1 · Inputs

What the agent operates on.

The 3-3-3 Method operates on a single, self-contained HTML artifact. Understanding what constitutes valid input is essential to the agent's success.

Required Input
One HTML file.

Can be a dashboard, report, visualization, training document, marketing page, one-pager, START-HERE, or any self-contained HTML artifact. The file must be complete enough to run independently in a browser — no external dependencies beyond Google Fonts or standard libraries. JavaScript is optional — static HTML/CSS documents (training docs, marketing pages) are fully supported.

Minimum Viable Input
What the file must contain.
  • HTML structure — Semantic markup with meaningful sections, headers, and data containers.
  • CSS — A working style system (variables, layout, responsive design).
  • JavaScript (optional) — Logic that processes or displays data. Not required for static documents like training docs or marketing pages.
Ideal Input
A working artifact that could be significantly enhanced.

The method works best on files that:

  • Are functionally complete and error-free
  • Have a clear purpose and audience
  • Lack depth features (drill-down, detail views, cross-filtering)
  • Are missing power-user features (export, search, comparison)
  • Could benefit from enhanced interactivity or data storytelling
Out of Scope
What the method does not do.

The 3-3-3 Method does not fix bugs, refactor architecture, or change the core data model. It adds features on top of a working foundation. If the input file has fundamental issues (broken layout, broken JavaScript logic, missing data), those must be resolved before improvement rounds can proceed.

Section 2 · Taxonomy

The ten improvement categories.

Each category is a class of user-facing improvements that make the artifact more powerful, more accessible, or more insightful. Categories 1–3 appear in Round 1, 4–6 in Round 2, 7–10 in Round 3 — a progression of increasing complexity and decreasing user frequency.

# Category Description Round
1Drill-Down & DetailClick aggregate data and see underlying details. Click-to-drill panels, expandable rows, modal detail views.R1
2Auto-Generated NarrativesTurn data into natural-language summaries that update dynamically. Executive paragraphs, insight bullets, trend narratives.R1
3Sortable & Filterable TablesClick-to-sort columns, inline filters, search-within-table, sticky headers on scroll.R1
4Hierarchical ExpansionNested organizational relationships. Manager → supervisor → site, nested tree expand/collapse.R2
5Export & PortabilityCopy-to-clipboard summary, print CSS, CSV/JSON export, shareable URL parameters.R2
6Anomaly & Outlier DetectionStatistical flagging. 2+ SD outlier highlighting, pulsing alert dots, trend-break detection.R2
7Statistical DepthCorrelation matrices, regression lines, percentile bands, distribution histograms.R3
8Visual BenchmarkingGoal lines at percentiles, quadrant coloring, peer overlays, industry benchmark bands.R3
9Search & NavigationType-ahead search, keyboard shortcuts, jump-to-section nav, highlight-on-map or in-table.R3
10Cross-Component LinkingClick matrix cell → scatter updates. Filter in one view → all views sync. Coordinated interaction.R3

Distribution across rounds.

Round 1 · Categories 1–3
Drill-Down · Narratives · Sort & Filter.

Foundation interactivity. Let the user pull apart the data and read the story it tells.

Round 2 · Categories 4–6
Hierarchies · Export · Anomaly Detection.

Deepen the model. Introduce structure, portability, and statistical flagging.

Round 3 · Categories 7–10
Statistics · Benchmarking · Search · Linking.

Power tools. Cross-component orchestration and analytical depth that make the artifact feel professional.

Section 3 · Log Format

The improvement-log spec.

A single HTML file — improvement-log.html — scaffolded at Step 0 and populated across Steps 4, 7, and 10. The canonical reference is 02-golden-example.html. Match that structure exactly.

File Location
One log per run.

Stored in the run folder:

runs/{NN}-{advisor-slug}/improvement-log.html

Log shape · top to bottom.

Six ordered sections — same order every time.

1 · Label + Title
Who the reviewer is, what the pass is about.

3-3-3 Methodology · Reviewer: {Advisor Name} label, then an H1 naming the artifact and the pass (e.g., "Training Package Landing Page — Typographic Pass"), then a 1–2 sentence subtitle framing what this pass was focused on and what came before it (if stacked).

2 · Summary Block — "Read This First"
Dark-background block placed before the rubric.

Contains: label "Summary · Read this first", headline "{Advisor}-graded: {v0 avg} → {v3 avg}", a narrative paragraph (2–4 sentences) explaining where the biggest lifts landed, which dimensions moved most, and why, then 4 summary stat tiles (rubric avg lift, improvements shipped, biggest-Δ dimension, one characteristic metric like "4 → 3 active display weights"). This is the most-read block in the log, so it leads. Populated only at the very end of the run (Step 10) — written last, displayed first.

3 · Rubric Card
4–6 dimensions with one-line definitions.

A single boxed block listing the 4–6 rubric dimensions the advisor is scoring against, each with a short one-line definition. This anchors all subsequent scores.

4 · Scoring Matrix
One table. Rows = dimensions. Columns = versions.

Columns: Baseline (v0), R1 (v1), R2 (v2), R3 Final (v3), Δ. Bottom row = Average. Populated progressively: v0 at Step 1, R1 at Step 4, R2 at Step 7, R3+Δ at Step 10.

5 · Three Round Sections
Round 1, 2, 3 — each with 3 improvement cards.

"Round 1 — {short theme}", "Round 2 — {short theme}", "Round 3 — {short theme}", each with a one-line sub-subtitle explaining the round's strategic focus. Under each round, 3 improvement cards (see below).

6 · Teach-Through-The-Framework Memo
Required closing section. The log is a teaching artifact.

Required closing section placed at the very bottom of the log, after the three round sections. This is where the agent teaches the user the advisor's framework through the specific edits that were just made. It must contain:

  • A 2–3 sentence plain-English restatement of the advisor's core mental model (e.g., Rider/Elephant/Path, or 45–75ch measure, or Pains/Gains/Jobs).
  • For each of the 9 improvements, a one-line "What to spot next time" teaching bullet that names the pattern, the cue that should have triggered it, and the corrective move.
  • A 3–5 item "Self-review checklist" the user can run on future artifacts without the agent.

The purpose is educational: the user should finish the log knowing how the advisor sees the world, not just what the agent changed. This section makes the log a teaching artifact, not just a changelog.

Improvement Card · 9 Total
One bordered card per improvement.
  • imp-label — "Improvement N · {Rubric dimension touched}" (e.g., "Improvement 3 · Reading Experience")
  • h3 — One-line title of the change, stated as the decision (e.g., "Body weight 300 → 400 (readability over fashion)")
  • Rationale paragraph — 2–4 sentences explaining why this change matters in the advisor's frame. Quote or paraphrase the advisor's principle.
  • Before/After code grid — Two columns. Left: red-border BEFORE with the prior code. Right: green-border AFTER with the new code. Both in monospace. Keep snippets tight — just enough to show the delta.

Example card HTML (from golden example)

<div class="imp">
  <div class="imp-label">Improvement 3 · Reading Experience</div>
  <h3>Body weight 300 → 400 (readability over fashion)</h3>
  <p>Inter 300 on white is thin, low-contrast, fashionable.
     Reichenstein: body weight exists to be read, not admired...</p>
  <div class="grid">
    <div class="before"><strong>Before</strong>body { font-weight: 300; }</div>
    <div class="after"><strong>After</strong>body { font-weight: 400; }</div>
  </div>
</div>
Design System · Match the Golden Example
Fonts, colors, labels — match verbatim.

Fonts: Inter (body), JetBrains Mono (labels, code, numeric cells). Colors: black (#000), white, grey scale (grey-100 → grey-700), green (#4a7c59) for AFTER/delta-positive, red (#dc2626) for BEFORE. Labels: 11px mono, 0.12em letter-spacing, uppercase, grey-500. Scoring matrix: monospace right-aligned numbers, green delta column, grey-100 Average row. Summary: black background, white text, 4-column stat grid with 32px mono stat values.

Section 4 · Patterns

Implementation patterns.

The agent adds features to the HTML artifact following strict patterns. These patterns ensure new code integrates cleanly with existing code, survives filter changes, and maintains the artifact's integrity.

CSS Pattern
Insert before the closing </style> tag.
  • Use the artifact's existing CSS variable names for colors (e.g., --primary, --text)
  • Add @keyframes for animations
  • Add @media print for print-friendly styles
  • Add @media (max-width: 768px) for responsive adjustments
  • Namespace new class names to avoid conflicts (e.g., .drill-down-modal, .filter-badge)
HTML Pattern
Insert new sections in logical positions.
  • New sections go between existing sections
  • New controls go near their related components (e.g., a sort button near the table header)
  • Overlays, panels, and modals go at the end of the body, just before </script>
  • Preserve all existing HTML; never delete or move existing elements
  • Use semantic HTML (e.g., <button>, <input>, <dialog>)
JavaScript Pattern
Insert before the closing </script> tag.
  • Write discrete functions for each feature (e.g., enableDrillDown(), addSearch())
  • Register new update functions in the master update function (called on filter change or initialization)
  • Add event listeners in the DOMContentLoaded block
  • Use the artifact's existing data structures — don't create parallel data stores
  • Reference the artifact's existing variables (e.g., data, filteredData, selectedFilters)
Integration Checklist
Verify after every feature.

After implementing each new feature, verify: CSS added and styled correctly, HTML container/element created and positioned logically, JavaScript function written and working, function called from the master update function (or on appropriate event), event listeners registered (click, input, change, etc.), feature survives filter changes (re-called when filters update), and no console errors or warnings.

Example · Adding a search feature.

Step 1 · Add CSS
Style the search box.
/* Search feature */
.search-box {
  margin-bottom: 1rem;
  padding: 0.75rem;
  border: 1px solid var(--border);
  border-radius: 4px;
}
Step 2 · Add HTML
Markup for the input.
<div class="search-box">
  <input type="text" id="search" placeholder="Search...">
</div>
Step 3 · Add JavaScript
Wire the listener and integrate.
function enableSearch() {
  const searchInput = document.getElementById('search');
  searchInput.addEventListener('input', (e) => {
    const query = e.target.value.toLowerCase();
    // Filter data based on query
    updateDisplay();
  });
}

// In DOMContentLoaded:
document.addEventListener('DOMContentLoaded', () => {
  enableSearch();
  updateDisplay();
});
Section 5 · Principles

Six core principles.

These principles ensure improvements are meaningful, user-centered, and aligned with the artifact's purpose. They keep the agent honest across every round.

Principle 01
Rubric Before Rounds.

Define what "better" means before suggesting improvements. An advisor-derived rubric anchors all three rounds, keeps the agent from drifting into taste-based edits, and gives the scoring matrix a measurable standard.

Principle 02
Action Produces Information.

The core principle. Each round reveals opportunities invisible before. When the user clicks to drill down, sorts a table, or performs a search, they gain new information or capability. Improvements should never be decorative — they should enable the user to do or understand something new.

Principle 03
Surgical, Not Radical.

Edit, don't rewrite. Preserve what works. The agent never rewrites the entire artifact, redesigns the layout, or changes the data model. It adds targeted features to the existing foundation — faster, safer, and respectful of the original design intent.

Principle 04
Connected, Not Siloed.

New features should link to existing ones wherever possible. A drill-down modal should respect the current filters. A search feature should update the table. An export function should include the current selections. Siloed features feel disconnected and limit user value.

Principle 05
Data-Driven, Not Decorative.

Every improvement should help the user understand the data better, not just look nicer. Colors, animations, badges, and visual effects should serve a purpose (highlighting outliers, showing state). Avoid cosmetic changes that add no information value.

Principle 06
Export-Ready.

The artifact should be able to communicate its insights outside of itself. Users should be able to copy summaries, download filtered data, print reports, or share states via URL. The artifact's value extends beyond the browser window.

Quick Reference

File structure and tracked metrics.

The canonical on-disk shape of a run, plus the metrics the agent tracks across rounds.

File structure after a full cycle.

project-folder/
├── artifact.html                          (original source — untouched)
└── runs/
    └── 01-{advisor-slug}/
        ├── v0-baseline.html               (copy of source at run start)
        ├── v1.html                        (after Round 1: improvements 1-3)
        ├── v2.html                        (after Round 2: improvements 4-6)
        ├── v3.html                        (after Round 3: improvements 7-9, final)
        └── improvement-log.html           (rubric, scoring matrix, 9 cards, summary)

# Multi-expert? Sequential stacking adds another run folder:
    └── 02-{next-advisor-slug}/
        ├── v0-baseline.html               (hard-copy of 01's v3.html)
        ├── v1.html / v2.html / v3.html
        └── improvement-log.html

Key metrics to track.

Lines of Code
BEFORE and AFTER for each round.

HTML + CSS + JS. Record both raw line counts and the delta per round.

Features Added
Count and name each feature per round.

Three per round, nine total. Each named in the improvement log and mapped to a rubric dimension.

Time to Implement
Optional; helps understand complexity.

Track only if useful for estimating future runs. Not required for the log.

User Impact
Qualitative description of what the user can now do.

One sentence per improvement, phrased from the user's point of view: "Can now drill from site totals to individual-day records in two clicks."
