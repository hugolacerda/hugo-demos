Production System · Process

The 3-3-3 Method
— Process

Step-by-step execution guide for Claude agents enhancing any HTML document — dashboards, training documents, marketing pages, reports, or interactive artifacts — through three coordinated rounds of improvement.

Phase 0 · Initialization

Catalog, baseline, advisor, rubric.

Before beginning any improvement work, establish a complete understanding of the artifact you're enhancing.

Init · Catalog & Baseline
Step · Init
Read everything. Map the file.
  • Read all 5 agent files (00 through 04) to understand the complete methodology and context taxonomy.
  • Read the target HTML file completely. For files >5000 lines, use offset/limit parameters strategically. Use grep to locate function definitions and key sections.
  • Create a baseline catalog including: total line count, number of JavaScript functions, interactive components (buttons, inputs, click handlers), external libraries and frameworks, data sources and how data flows through the artifact.
  • Identify the master update function. This is the function called when state changes (e.g., updateAllCharts(), render(), refresh()). All Round 1, 2, and 3 features must integrate by being called from this function. If no master function exists, you will create one in Phase 1.
  • Set up a tracking list with all 11 steps marked as pending.

Initialization checklist

  • Read all methodology files (00–04)
  • Complete file read (in sections if necessary)
  • Baseline metrics documented
  • Master update function identified
  • 11-step progress tracker created
Step 0 · Select Advisor & Create Snapshots
Step 0
The advisor IS the rubric.

The advisor is the named expert whose methodology provides the rubric. Before any scoring, propose 3 candidates matched to the artifact type and let the user choose.

  • Propose 3 advisor candidates. Landing / sales page → Peep Laja (CRO), Harry Dry (copy), April Dunford (positioning). Design / typography / UX craft → Oliver Reichenstein, Dieter Rams, Edward Tufte. Dashboard / data viz → Edward Tufte, Stephen Few, Cole Nussbaumer Knaflic. Training / start-here docs → Julie Dirksen, Cathy Moore, Andy Matuschak. Strategy memo / business case → Richard Rumelt, Roger Martin, Jeff Bezos (6-pager).
  • Advisor selection — propose 3 advisor options with rationale, pick the single most impactful one, and proceed. User can override at end-of-run review.
  • Check the user's advisor library — look in 3. Marketing/2. Advisors/, 4. Sales/Advisors/, and any other domain Advisors/ folder relevant to the artifact. Search by author slug (e.g., heath-switch-advisor.html). If the advisor already exists, read it to derive the rubric in Step 1.
  • If the advisor does NOT exist: create the advisor file before continuing. Save it to the domain-appropriate Advisors folder. Match the existing advisor-file format in that folder (HTML in Marketing, MD in Sales). The file must contain: masthead with advisor name + domain, 2–3 sentence intro, the 4–6 scorable rubric dimensions (this IS what the 3-3-3 agent will read back on future runs), the advisor's core mental models / frameworks, 4–6 signature moves, 3–5 common mistakes the advisor would flag. This makes the advisor reusable.
  • Create the run folder at runs/{NN}-{advisor-slug}/ next to the source file. NN is a zero-padded sequence number (01, 02…).
  • Copy the input into the run folder as v0-baseline.html. If prior runs exist and the user wants sequential stacking, v0 is a hard-copy of the prior run's v3.html.
  • Create an empty improvement-log.html in the run folder, scaffolded to match the golden example (rubric card, scoring matrix with v0 column, empty round sections).
  • Never edit the source file. All edits in Steps 3, 6, 9 apply to the per-round snapshots inside the run folder only.
Outcome · Advisor confirmed by user. Run folder created with v0-baseline.html and scaffolded improvement-log.html. Source file untouched.
Step 1 · Derive Rubric From Advisor
Step 1
4–6 scorable criteria from published methodology.

The rubric is derived from the chosen advisor's published methodology — not invented. Read the advisor's frameworks, heuristics, and published criteria, then translate them into 4–6 scorable dimensions for this artifact.

  • Extract 4–6 criteria from the advisor's published work. Peep Laja → Clarity, Relevance, Value, Friction, Distraction, Anxiety. Reichenstein → Typographic Hierarchy, Vertical Rhythm, Type Discipline, Reading Experience, Content-First, Macrotypography. Tufte → Data-Ink Ratio, Small Multiples, Chartjunk, Layering & Separation.
  • Score the baseline snapshot against each criterion (0–10 per criterion) before suggesting any improvements.
  • Keep the rubric stable across all 3 rounds. Do not change the criteria mid-run unless the user changes the advisor.
  • Rescore at Steps 4, 7, and 10 using the same criteria to show honest movement.
Outcome · Advisor-derived rubric recorded with baseline scores, before any suggestions are made.
Phase 1 · Round 1

Foundation improvements.

The first round establishes foundational interactivity and context. Focus on the highest-impact gaps that unlock downstream possibilities.

Step 2 · Suggest 3 improvements
Analyze against the rubric and gap categories.

Review the artifact against the Step 1 rubric and four key gap categories (see 04-context.html for the full taxonomy):

Gap CategoryWhat to Look ForExample Questions
Interactivity GapsData shown but not actionable or explorableCan users drill down? Click to filter? Sort dynamically?
Missing ContextNumbers lack benchmarks, comparisons, narrativeIs performance vs. target shown? Past vs. present? Best vs. worst?
Navigation GapsUsers struggle to find specific items quicklyIs there search? Filtering? Logical grouping?
Export GapsInsights cannot leave the artifactCan insights be copied? Printed? Downloaded?

Suggestion format

For each of the 3 improvements, provide:

  • Name: short, descriptive title
  • Description: 2–3 sentence explanation of what it adds
  • Why It Matters: user-facing value or analytical benefit
  • Rubric Link: which rubric criterion this improves most
Outcome · Default mode: run the full 3-round loop end-to-end without check-ins. Present proposals in the improvement log, implement, and continue. User reviews at the end. Only pause mid-run if the user explicitly requested per-round confirmation in the brief.
Step 3 · Implement 3 improvements
Copy v0 → v1, then edit v1 only.

Implementation pattern

For each improvement, add code in this order:

  • CSS Styles — insert before </style>. Use the color palette from the design system. Follow existing naming conventions.
  • HTML Elements — insert in the appropriate location in the body. Match existing markup patterns and indentation.
  • JavaScript Functions — insert before </script>. Use descriptive function names. Comment non-obvious logic.
  • Integration — add function calls to the master update function. Ensure new features are initialized on page load.
  • Event Listeners — attach to appropriate elements in the initialization block. Test click handlers, change listeners, form submissions.

Implementation guidelines

  • First, copy v0-baseline.html to v1.html inside the run folder. This preserves v0 as the untouched starting point.
  • All Edit operations target v1.html — never the source file, never v0.
  • Use targeted Edit operations — never rewrite the entire file.
  • One improvement at a time — implement, verify, document before moving to the next.
  • Preserve existing functionality — your additions should not break anything.
  • Keep consistency — match the existing code style, spacing, and structure.
Outcome · All 3 Round 1 improvements applied to v1.html. v0-baseline.html is untouched. Verify v1 still loads and functions correctly.
Step 4 · Write improvement-log.html (Round 1)
Document the transformation.

Create a new file documenting the transformation. Include:

  • Before/After Metrics — line count: X → Y (Z new lines added), number of functions: X → Y, interactive components: X → Y.
  • For each improvement (1–3): improvement name and brief description, code locations (file section, line ranges if helpful), before/after narrative (1–2 paragraphs), impact statement — how this changes the user experience.
  • Rubric Scorecard — score the current artifact against each Step 1 rubric criterion. Note where the biggest gaps still remain heading into Round 2.
Outcome · Improvement log written and saved at /path/to/artifact/improvement-log.html with the Round 1 section populated.
Phase 2 · Round 2

Deepening improvements.

The second round builds on Round 1's foundation, creating connections between new features and introducing analytical depth.

Step 5 · Suggest 3 more improvements
Round 2 thinking.

Re-read the target file — it has changed since Round 1. Look for opportunities that Round 1 created and for rubric criteria that still score weakly:

  • Cross-component connections — can new components interact with existing ones? Example: Clicking a cell in a new data matrix drives an existing chart.
  • Drill-down patterns — can aggregate views now support more granular exploration? Example: Manager-level view → drill to supervisor level.
  • Export & communication — can the artifact now export insights? Example: Copy insights to clipboard, print-friendly CSS, downloadable data.
  • Statistical methods — can analytical depth increase? Example: Anomaly detection, correlation matrices, trend analysis.
Outcome · Document 3 improvements that leverage Round 1's new features in the improvement log, then implement. No mid-run confirmation.
Step 6 · Implement 3 improvements
Copy v1 → v2. Integrate with Round 1.

Follow the same pattern as Step 3, with special attention to:

  • Integration with Round 1 features — new functions should call (or be called by) Round 1 functions. Event listeners should trigger related updates across components.
  • Dependency management — ensure Round 1 features are always available before Round 2 features try to use them.
  • Master function updates — add calls to new Round 2 functions in the master update function.
Outcome · Before editing, copy v1.html to v2.html. All 3 Round 2 improvements applied to v2.html. v1 stays frozen as the Round-1 artifact.
Step 7 · Append Round 2 to improvement-log.html
Same format as Round 1.

Document improvements 4–6 and rescore the snapshot against the advisor's rubric.

Outcome · Round 2 section appended at /path/to/artifact/improvement-log.html.
Phase 3 · Round 3

Polish and power features.

The final round adds the "wow" features — sophisticated analytical capabilities, visual intelligence, and instant access patterns that make the artifact feel like a professional tool.

Step 8 · Suggest 3 final improvements
Round 3 thinking.

Re-read the file again (now significantly larger and more feature-rich). Focus on the highest remaining rubric gaps and on:

  • Statistical depth — correlation matrices between key metrics, regression lines or trend forecasting, benchmarking overlays (industry standard, peer comparison), anomaly highlighting and root cause analysis.
  • Visual intelligence — goal lines and performance bands on charts, quadrant analysis (2×2 matrices with interpretation), color coding for status, variance, or performance tiers, sparklines or micro-trends next to scalar values.
  • Instant access — search/type-ahead for finding specific items, keyboard shortcuts for power users, favoriting or pinning high-value views.
  • Cross-component orchestration — one component interaction drives multiple downstream updates, cascading filters across the entire artifact, state synchronization across independent views.
Outcome · Document 3 high-impact, sophisticated improvements in the improvement log and implement. These should feel like professional polish. No mid-run confirmation.
Step 9 · Implement 3 improvements
Copy v2 → v3. Edit v3 only.

First, copy v2.html to v3.html. Edit v3.html only — never the source file, never earlier snapshots. Use grep strategically to locate insertion points. Ensure all new features integrate cleanly with Round 1 and Round 2 edits.

Outcome · All 3 Round 3 improvements applied to v3.html. v0, v1, v2 all untouched. Verify full functionality.
Step 10 · Finalize improvement-log.html
Final log format.

Finalize the log so it matches the golden example (02-golden-example.html):

  • Improvements 7–9 documented individually as before/after code grid cards.
  • Scoring matrix fully populated: v0 → v1 → v2 → v3 → Δ for each rubric dimension, plus Average row.
  • Closing summary block (mandatory): short headline restating the final average score (e.g., "Reichenstein-graded: 5.8 → 8.0"); narrative paragraph — where the biggest lifts landed, which dimensions moved most, and why; summary stat tiles (rubric avg lift, improvements shipped, biggest-Δ dimension, any before/after count that matters).
Outcome · Final improvement log completed at /path/to/artifact/improvement-log.html. All 11 steps complete. Source file untouched.
Reference · Edge Cases

Special scenarios.

Strategies for non-standard inputs and situations where the default loop needs adjustment.

Edge Case 1 · Large files (>5000 lines)
Don't read the entire file at once.
  • Read the file in sections (e.g., first 1000 lines, then 1001–2000)
  • Use grep to locate function definitions, event listeners, and the master update function
  • Create a map of where code should be inserted
  • Read strategically around insertion points
Edge Case 2 · No master update function
Create one.

In Step 3, before implementing the first improvement:

  • Create a function (e.g., updateArtifact()) that calls all initialization and update functions in sequence
  • Call it from DOMContentLoaded
  • Use this function as the integration point for all Round 1, 2, and 3 features
Edge Case 3 · Non-interactive starting file
Round 1 should add interactivity first.

Focus improvements on:

  • Click handlers and filtering
  • Dynamic content rendering
  • Form inputs that drive state changes

Round 2 and 3 then build analysis and power features on top of this interactive foundation.

Edge Case 4 · User wants to skip a round
Allow it.

If a user says "skip Round 2, go straight to Round 3":

  • Implement only the requested round(s)
  • Still write an improvement log documenting what was completed
  • Note in the comparison that earlier rounds were skipped
Edge Case 5 · Improvement requires restructuring
Suggest an alternative.

If an improvement would require rewriting >30% of the file:

  • Explain the constraint to the user
  • Propose an alternative improvement that achieves similar value with less disruption
  • Document reasoning in the log, then implement
Edge Case 6 · Context compaction mid-run
Recover your state.

If context resets during a multi-step run:

  • Re-read the latest round's snapshot (v1.html, v2.html, or v3.html) in the run folder
  • Re-read the advisor-derived rubric (Step 1)
  • Re-read the last completed round in improvement-log.html
  • Identify which step is incomplete
  • Resume from the next incomplete step with full context

Principles

Seven rules that keep the method honest.

These are the guardrails. Violate any one and the comparison chain breaks.

Principle 0
Never edit the source file.

All edits apply to per-round snapshots inside runs/{NN}-{advisor-slug}/ (v1 for R1, v2 for R2, v3 for R3). The source file and v0-baseline are immutable — preserved so the user can diff across rounds, compare before/after visually, or run another advisor's pass.

Principle 1
One improvement at a time.

Implement, verify, and document each improvement before moving to the next. This makes debugging easier and keeps the artifact stable.

Principle 2
Preserve existing functionality.

Your additions should never break what was already working. Use targeted edits, not wholesale rewrites.

Principle 3
Integration is everything.

A feature that isn't wired into the master update function is incomplete. Always ensure new code is called and receives data.

Principle 4
Build on your own work.

Round 2 features should leverage Round 1. Round 3 features should leverage both. Cross-component linking multiplies value.

Principle 5
Document as you go.

Improvement logs are not afterthoughts — they capture the transformation for the user and provide recovery points if context resets.

Principle 6
Communicate constraints.

If an improvement is impossible, too disruptive, or blocked by architecture, explain why and propose an alternative.

Final checklist

Before declaring all 11 steps complete:

  • Source file untouched
  • All snapshots (v0→v3) saved to the run folder and loading without errors
  • All Round 1, 2, 3 features are integrated and functional
  • Improvement log (improvement-log.html) covers all 9 improvements
  • Advisor's rubric used to score every round
  • Cumulative progress narrative is complete
  • No pre-existing functionality was broken
