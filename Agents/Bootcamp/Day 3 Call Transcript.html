Run the Agent. Watch It Work.

A short clinic session: watching an agent execute its review pass, fielding install-and-file-format questions from the cohort, and clearing the runway for the rest of the build.

Opening — Watching the Agent Run

The session opened mid-execution. The agent students built in Day 2 was actively running in front of the cohort, and Katie was narrating what it was doing in real time — moving through its instruction file, checking what file it was looking for, what folder it lived in, what format it expected.

Katie Where's that folder? Where's that file? And what format is it in? It's going to tell me — and turn that into what we call a gap.

The agent's job in this run: read the rest of its own instructions, pull the source material it was pointed to, and produce nine improvements on the work the student had already created. Katie kept the framing simple — the agent isn't doing magic. It's reading the files in the order they're numbered, doing the work in the order it was told, and handing back a deliverable.

What the agent is producing Nine improvements on the existing draft, plus a wrap-up containing two small scripts that can be deployed without disturbing the rest of the build. The improved version comes back as an HTML deliverable.

Lead Gen, Wrap-Ups, and Publishing

A student called out the lead-gen angle — once the agent finishes, the wrap-up is publishable. That's the part that matters. The agent's output isn't a draft you sit on; it's something that goes live and starts working.

Student And lead gen.
Katie Yeah. Isn't that fun? You publish a wrap-up. It has two small scripts without disturbing anything else. Here's the improved version. Here's the action.

The pattern Katie was reinforcing here: the agent doesn't just produce content. It produces content and the small executable pieces that go with the content — the scripts, the next-step actions, the publish-ready artifact. That's what separates an agent from a fancy autocomplete.

If the Agent Doesn't Finish in Session

Because the agent was still running and the cohort was on the clock, Katie set a clear expectation about what happens if the run doesn't complete before the session ends.

Katie You are welcome to do that. But if this agent doesn't finish running during today's session, I will take the final HTML deliverable and save it in the Basecamp so you can see what this final step looks like.
Where the deliverable lives Final HTML output from the agent's run will be posted to Basecamp by Katie if the run doesn't complete live. Students don't need to babysit the run — the file will be there.

With that, she turned it over to the cohort for questions.

Q&A

Katrina — File Folder vs. HTML File

Katrina raised the issue that surfaced when she went to open her own five-file structure. Her file icons weren't displaying the way Katie's were on screen.

Katrina Every time you open up one of your five-step files, your HTML — your golden rule is 02, and it shows the HTML. Mine shows a file folder for that. So I have HTML file folder, HTML, HTML, HTML. I have to click on the file folder to get in. The folder comes over and it says zero bytes even though it's full.
Katie Did you follow —

The exchange points to a real install-side gotcha: when an HTML file gets saved as a folder of supporting assets (the way some browsers package a saved page), the file system shows a folder icon and reports zero bytes even though the underlying content is there. The fix is to make sure the file was saved as a single .html document, not as "Webpage, Complete" or an HTML archive that splits the page into a folder of pieces.

Watch-list for the cohort If your numbered file shows up as a folder instead of a single HTML file, you almost certainly saved it in a format that bundled the assets separately. Re-save the source as a single .html file. The folder reporting "zero bytes" is the tell.

<lesson_summary>

core_thesis: An agent's job is to read its instruction files in order, do the work, and hand back both a deliverable and the small executable pieces that go with it. The whole point of the numbered five-file structure is that the agent can read itself — which means the student doesn't need to babysit it. When something goes wrong, it's almost always at the file-system level, not the AI level.

key_concepts:

[CONCEPT 1: The Agent Reads Itself]
The agent is doing exactly what its files told it to do, in the order the files are numbered. When Katie narrates "where's that folder, where's that file, what format is it in," she's reading what the agent is doing — not steering it. The file structure is the instructions.

[CONCEPT 2: Deliverable + Action, Not Just Content]
A finished agent run produces two things: the improved deliverable (the HTML wrap-up) and the small scripts or next-step actions that go with it. If your agent only spits out content, you've built a fancy autocomplete. If it spits out content plus the executable pieces, you've built an agent.

[CONCEPT 3: The Run Doesn't Need Your Eyes On It]
Agents run asynchronously. If a run doesn't finish in the session, it still finishes. Katie's commitment to drop the final HTML in Basecamp reinforces this — the student's job is to set the agent up correctly, not to watch every token stream by.

[CONCEPT 4: File Format Is Where Beginners Lose Hours]
Katrina's issue — HTML files showing as folders reporting zero bytes — is the canonical beginner trap. Browsers can save a webpage as a single .html document or as "Webpage, Complete" which bundles a folder of assets. The latter looks like the file is missing or empty. It's not. It's just packaged wrong for the agent to read.

vocabulary:

  • Five-file structure — the numbered folder system that all bootcamp agents are built inside. Day 1 set this up; everything since then has lived inside it.
  • Golden rule / golden example — the 02 file in the structure. The reference example the agent uses to know what "good" looks like.
  • Wrap-up — the publishable deliverable the agent produces at the end of a run, including its scripts/actions.
  • Gap — what Katie calls the difference between what the agent finds and what it expected, which becomes the basis for its improvement suggestions.
  • Basecamp — the cohort's shared workspace where final deliverables and recordings are posted.

<homework_walkthrough>

Day 3 was a short clinic session, so the "homework" here is really a verification pass: make sure the agent build from Day 2 is structurally sound before Day 4. Walk the student through this step by step.

STEP 1: Verify your five-file structure
What: Open the folder where your agent lives. Confirm you see five numbered files (01, 02, 03, 04, 05).
Why: The agent reads in numerical order. If a file is missing or out of order, the agent will skip or stumble.
Success Criteria: Five files. Numbered. Each one opens as a single HTML document, not a folder.
Coach the Student: If they hesitate on whether a file is a "single HTML document" or a "folder," have them right-click and check the file type. On Mac it's "Kind." On Windows it's "Type." It should say "HTML Document" or similar — not "Folder."

STEP 2: Resolve any folder-instead-of-file issues
What: If any of the five files shows up as a folder reporting zero bytes, re-save the source content as a single .html file.
Why: The agent can't read a packaged-webpage folder the same way it reads a clean HTML document. This is the most common Day-3 blocker.
Success Criteria: All five files are single HTML documents. No folders in the structure.
Coach the Student: If they're saving from a browser, the trick is "Save Page As → Webpage, HTML Only" (not "Webpage, Complete"). If they're exporting from Claude or ChatGPT, the file should already be a single .html — but they should still right-click and confirm.

STEP 3: Pull the finished Day 2 deliverable from Basecamp (if your run didn't finish live)
What: Check Basecamp for the final HTML deliverable Katie said she'd post.
Why: Even if your run completed, comparing your output to the version Katie posts is a free quality check.
Success Criteria: You've got the reference version saved next to your own output.
Coach the Student: If they don't see it yet, tell them not to panic — Katie posts things after sessions, not during. Check back later in the day.

STEP 4: Read your own wrap-up
What: Open the HTML deliverable your agent produced. Read it like a publishing editor.
Why: You're not just checking that it ran. You're checking whether the nine improvements actually improve anything, and whether the two small scripts/actions are publishable as-is.
Success Criteria: You can name at least three of the nine improvements and explain why each one is an improvement. You've identified the two scripts/actions and you know what they'd do if you ran them.
Coach the Student: If they can't explain the improvements in their own words, the agent didn't work — or the agent worked but the student didn't read carefully. Either way, that's the next conversation.

<common_stumbling_points>

  • "My file shows as a folder." The browser saved the page as a bundled webpage. Watch for this — it's almost always the first thing that goes wrong. Redirect: "Re-save as HTML Only, not Webpage Complete."
  • "My agent didn't finish running." Many students assume this means something is broken. It doesn't. Redirect: "Did Katie post the final to Basecamp? Pull it from there and compare."
  • "My output is just text. Where are the scripts/actions?" The student may have built the agent without the wrap-up logic. Redirect them to verify file 03 or 04 (the process file) actually instructs the agent to produce the action pieces.
  • "How do I know if my agent is good?" Watch for students who want to evaluate the agent before they can evaluate the output. Redirect: read the wrap-up. If you can't explain the improvements in your own words, the agent didn't work for you yet.
  • "Should I rebuild from scratch?" Almost always no. Watch for the impulse to scrap-and-restart instead of debugging. Redirect: "What's the smallest fix that gets you to a working file structure?"
